## Phase 0 — Foundation (orchestrator)

1. **`CLAUDE.md` moved from `docs/` to the repository root.** — It was uploaded into `docs/`; agents and the plan expect it at the root. `docs/ORCHESTRATOR_PROMPT.md` is kept unchanged.
2. **Expo SDK 58** (latest stable on npm at build time: expo 58.0.26, React Native 0.88, React 19.3, TypeScript 6). — Plan says "latest stable SDK". Expo Go on the phone must be a build that supports SDK 58.
3. **Scaffolded from `create-expo-app` default template, then stripped.** Removed example screens and template-only packages (`@expo/ui`, `expo-glass-effect`, `expo-symbols`, `expo-image`, `expo-device`, `expo-web-browser`) to keep the dependency list minimal. React Compiler experiment is off (fewer moving parts while debugging gestures).
4. **Routes live in root `app/`** (as in `CLAUDE.md`), not the template's `src/app/`. `@/*` maps to `./src/*`.
5. **Web output `single`** (one `index.html` SPA) instead of `static`/`server`. — GitHub Pages is static hosting; all data is client-side, and dynamic routes (`/team/[teamId]`) can't be pre-rendered. Deep links on Pages are handled by copying `index.html` to `404.html` at deploy time.
6. **Dependencies added** (all via `EXPO_OFFLINE=1 npx expo install`, because the sandbox can't reach `api.expo.dev`; versions come from Expo's bundled compatibility list):
   - `zustand` — state (plan). `@react-native-async-storage/async-storage` — persistence (plan).
   - `zod` — import-file and form validation (plan).
   - `expo-crypto` — `randomUUID` ids (plan).
   - `expo-file-system`, `expo-sharing`, `expo-document-picker` — native export/import (plan).
   - Dev: `jest`, `jest-expo`, `@testing-library/react-native` v14 (+ its peer `test-renderer@1.3`), `eslint`, `eslint-config-expo`, `prettier`, `eslint-config-prettier`, `eslint-plugin-prettier`, `@types/jest`.
7. **RNTL v14 is async**: `await render(...)`, `await fireEvent.press(...)`. — v14 is the version compatible with React 19.3.
8. **One Zustand store (`useAppStore`)** holding profiles/teams/players/matches + `currentProfileId`, persisted under AsyncStorage key `volley-lineup`, store version `1` with a `migrateStore` hook (`src/store/migrations.ts`). `hydrated` is runtime-only; the root layout shows a spinner until rehydration finishes so screens never render empty data first.
9. **Cascading deletes**: deleting a profile deletes its teams; deleting a team deletes its players and matches; deleting a player clears it from every lineup slot/libero of that team's matches.
10. **New matches start with one set (set 1, empty, we serve first).** Further sets are added when the user opens the set tab (`setLineup` inserts/replaces by `setNumber`, sorted). `Match.sets` stays length 1–5.
11. **Zustand v5 + derived arrays**: list selectors are exposed as hooks in `src/store/hooks.ts` using `useShallow`, to avoid the infinite re-render trap of returning fresh arrays.
12. **Strings split per feature**: `src/i18n/en.ts` holds shared strings and merges `src/i18n/en/{roster,lineup,rotation,transfer}.ts`. — Four workers adding strings to one file would conflict constantly. (v2: components get the strings for the current language with `useT()` from `src/i18n`; see #69.)
13. **Validation contract defined up front** in `src/domain/lineupValidation.ts` (stub on `main`): `validateLineup(set, players): ValidationResult` returning error/warning **codes** (no text in the domain layer; UI maps codes to i18n strings).
14. **Screens / routes**:
    `/` profile picker · `/teams` · `/team/[teamId]` (Roster | Matches tabs) · `/team/[teamId]/player?playerId=` (modal, add/edit) · `/team/[teamId]/match-new` (modal) · `/match/[matchId]?set=N` (Match screen = set tabs + lineup builder, i.e. plan screens 5 and 6 combined) · `/match/[matchId]/rotation?set=N` · `/match/[matchId]/starters` · `/settings`.
    — Combining Match + Lineup builder saves a navigation step; the set tabs sit directly above the court.
15. **Court orientation**: net at the top, front row 4-3-2 directly under it, back row 5-6-1 below (as seen from behind our own baseline). Orange court, white lines/net.
16. **Text on orange/yellow is near-black (`#0D0D0D`)**, not white — white on `#FF6B00` is ~2.9:1 and fails WCAG AA; black is ~7:1. Blue `#0057B8` is only used as a fill; text/links use `#3D8BFF`.
17. **Position badge colours**: S yellow, OH light blue, MB green, OPP purple, L white, DS grey — all with near-black text (AA).
18. **Wide layout breakpoint 768 px** (`useIsWide()`): court left, bench right above it; stacked below.
19. **Jest infrastructure** — `jest.setup.ts` mocks `react-native-worklets` with its shipped mock and stubs Reanimated's `initializeReanimatedModule` (it throws on `setCSSEventHandler` under JSReanimated in 4.7), so `react-native-reanimated/mock` loads and gesture-handler v3 hooks work in tests. Global test timeout 30 s, because route-level `renderRouter` tests take > 5 s on a cold cache. `.claude/` (agent worktrees) is ignored only at the repo root.

## Phase 1 — Feature decisions (from worker PRs)

### Rotation & validation (Worker B, PR #2)

20. **`NO_SETTER`** is only raised once at least one slot is filled. A secondary `S` position counts as a setter; unknown ids don't.
21. **`UNUSUAL_LAYOUT`** looks only at primary positions. It fires when the single primary S and the single primary OPP aren't opposite (positions differ by 3), or when exactly two primary MBs aren't opposite. A 6-2 (two setters) gives no layout warning.
22. **Issue grouping**: `INCOMPLETE` is one issue listing all empty positions; `DUPLICATE_PLAYER` is one per duplicated player; `UNKNOWN_PLAYER` is one per slot plus one for the libero.
23. **`getRotation(slots, n)`** accepts only 1–6 (throws `RangeError`); `rotateBy` takes any integer and wraps.
24. **Swipe**: left = next rotation, right = previous, 50 px threshold. Prev/Next buttons and a 1–6 stepper always work.
25. **Server highlight**: position 1 is always marked as server (plan §3.6). When the opponent serves first, the set shows "We receive first" instead of changing the highlight.
26. **Court contrast**: the court's own position numbers are hidden in the rotation screens; spots use blue (front row) / dark (back row) fills with white text, since white on orange fails AA.

### Profiles, teams & roster (Worker A, PR #3)

27. **"Injured" = `active: false`** — the data model has one flag.
28. **Startup redirect**: `/` forwards to `/teams` once per app session, only if `currentProfileId` points to an existing profile. The first visit to any roster screen consumes it, so deep links never cause a later redirect.
29. **Form limits**: jersey number 0–99 (unique per team, excluding the player being edited), names ≤ 40 characters, season optional ≤ 20 characters, at least one position (first = primary).
30. **New match** replaces the modal with the match screen, so Back from the match goes to the team.
31. **Confirm dialogs are in-app** (`Alert.alert` does nothing on web).
32. **react-native-web ignores `accessibilityState`** — roster controls also set `aria-checked` / `aria-selected`. The whole switch row is the touch target (≥ 44 px); the web Switch thumb colour is passed via `src/lib/switchProps(.web).ts`.

### Lineup builder (Worker C, PR #4)

33. **A set is stored on its first real edit**, not when its tab is opened, so browsing never creates empty sets and `match.sets` stays ≤ 5 and sorted.
34. **Copy from previous set** copies the six starters and the libero, not the serve choice.
35. **Making a court player the libero** sends the old libero to the bench.
36. **Drag activation**: on web after 6 px of mouse movement; on phones after a 200 ms long-press so swipes still scroll (`src/lib/dragActivation(.web).ts`). A press within 250 ms after a drag is ignored. Drops are hit-tested on the JS thread against measured zones (`src/lib/measureInWindow.ts`).
37. **Layout**: on phones the whole page scrolls and the bench is a wrapping grid; on wide screens the bench scrolls on its own (gesture-handler `ScrollView`).

### Export / import (Worker D, PR #1)

38. **Merge** matches items by id and the imported one wins; nothing is deleted. If the result would be inconsistent (e.g. two players with the same number in a team), the merge is refused with `MERGE_CONFLICT` and the user is told to use Replace.
39. **Unknown keys in a file are dropped**, not rejected. Import validates references (ids, team/profile links, jersey numbers, set numbers, lineup players belonging to the team, no player twice in a set, libero not on court), but not the soft lineup warnings.
40. **Sets are sorted by `setNumber` on import.**
41. **After an import**, if no valid profile is selected and the data has exactly one profile, it is selected. Otherwise the user picks one.
42. **Switch profile** in Settings clears the selection and returns to `/`. **Delete all data** stays on Settings so the user can import straight away.
43. **Native picker accepts any file type** (Android often mislabels `.json`); validation rejects anything that isn't a Volley Lineup file.

Sub-path build verified locally.

Releases are versioned: pushing tag `vX.Y.Z` (must match `version` in app.json and package.json) publishes release `vX.Y.Z` with asset `volley-lineup-X.Y.Z.apk`; `android.versionCode` is derived from the version (1.2.3 → 10203) in `app.config.js` so new APKs install as updates. Signed with the Expo template’s fixed debug key — fine for sideloading and updates, not for the Play Store. Package id `com.volleylineup.app`.

An emulator run of the release APK (`.github/workflows/android-smoke.yml`) showed navigation works, but nothing signalled that a profile row opens it (only Rename/Delete looked like actions). The emulator smoke test now also checks team creation and that an app restart lands back on Teams.
53. **Android emulator smoke test is manual-only** (`android-smoke.yml`, `workflow_dispatch`). It builds an x86_64 release APK, boots an API 30 emulator and drives the app with `adb` (`scripts/android-smoke.sh`), failing if an expected screen is missing. ## v2

54. **v2 data model** (orchestrator, before the v2 workers): `SetLineup.liberoReplaces: string[]` and `SetLineup.events: SetEvent[]` (an event log; score/rotation/server/subs are derived by a pure replay function, so undo is "drop the last event"). Export `schemaVersion` 2 — v1 files are upgraded on import (sets get empty `liberoReplaces`/`events`). Store version 2 with a v1→v2 migration; new persisted `language: 'en' | 'de'` (a device setting, not exported, kept on "Delete all data").
55. **Cloud sync is out of scope for v2** — it needs a backend and real accounts, which v1 deliberately avoided (no server, data stays on the device). Export/import remains the way to move data.
56. **Copy from previous set** now also copies whom the libero replaces; the copy's event log starts empty.

### Printable lineup sheet (PR #11)

57. **Print theme**: black on white, A4 portrait, separate from the dark app theme (`src/theme/print.ts`). The sheet HTML is built by a pure function (`src/domain/lineupSheet.ts`); every piece of user text is HTML-escaped.
58. **Web prints from a hidden iframe** (not `window.print()` on the app page), so web and phone use the same HTML; the page title is swapped to the sheet title while the dialog is open. **Phone**: `expo-print` → A4 PDF (34 pt margins) → share sheet; the PDF keeps the file name `expo-print` generates.
59. **Content**: only stored sets are printed ("No lineups yet" otherwise); court grid per set, libero, "Libero replaces #x, #y", who serves first; roster of all team players with position codes and injured marker. A 5-set match with 12 players fits one A4 page; long rosters break across pages.
60. **New dependencies**: `expo-print` (PDF on phones); dev `jsdom` + `@types/jsdom` (declared explicitly for the web print test; they were already present transitively via jest-expo).

### Libero swaps + 5-1 / 6-2 templates (PR #13)

61. **Libero swap rule**: the libero stands in for a chosen starter at back-row positions 5 and 6, and at position 1 only when that position is not serving. The rotation viewer treats position 1 as serving. One libero: if two chosen starters are in the back row, the first in `liberoReplaces` is replaced.
62. **Default "libero replaces"**: the primary middle blockers, pre-selected only when a libero is first assigned and nobody is chosen; later choices (including nobody) are kept; "Suggest middles" re-applies it. `liberoReplaces` only ever lists players on court.
63. **Template layouts** (rotation 1, setter serving): 5-1 = S1 · OH2 · MB3 · OPP4 · OH5 · MB6; 6-2 = S1 · OH2 · MB3 · S4 · OH5 · MB6 (hitter spots take an OH, else an OPP). Picked by primary position, then fallback role, then secondary position, lowest number first; only active players, never the libero or a primary-L player. Filling keeps libero, serve choice and events, resets `liberoReplaces` to the new middles, and is disabled for played sets.
64. **"Show libero swaps" toggle** in the rotation viewer: on by default, not persisted. The starters overview shows the base lineup. `ToggleRow` became a shared component (`src/components`).

### Live match + substitutions (PR #12)

65. **Set point = one point from winning**: target − 1 or more and ahead (target 25, 15 in set 5, win by 2, deuce included). PLAN §11.3's "2-point lead" would describe a set already won. Set ends are not enforced; a won set shows "won the set".
66. **Substitutions**: max 6 per set (`SUB_LIMIT` warning beyond); re-entry rule pairs a substitute with the player they replaced, and only that pair may swap back, once (`REENTRY_RULE`). Warnings never block; bench chips preview the warning before the tap. Impossible subs are skipped (`INVALID_SUB`). The libero is never a sub; tapping the libero on the live court substitutes the real player they stand in for.
67. **Live state** is replayed from `events` by `replaySet` (fields `slots`, `serverId`, `rotation`, `setPoint`, `setWinner`, … — named slightly differently from the PLAN §12 sketch). Live mode needs all six positions filled. `liberoReplaces` refers to starters: a substitute for a chosen middle isn't swapped for the libero.
68. **Lineup lock**: once a set has live events, its starting six, libero and first serve can't be edited (the replay depends on them); "whom the libero replaces" stays editable. "Reset live data" in live mode (with confirmation) clears the events and unlocks it. A rally, Undo, Reset or switching sets cancels a half-finished substitution.

### German translation (PR #14)

69. **`useT()` hook** (`src/i18n/index.ts`): components read the strings for the store's `language`, so every mounted screen re-renders on a switch without remounting navigation. Helpers outside components take `t` as a parameter; UI state keeps data, not finished text. An ESLint rule forbids importing `src/i18n/en` / `de` directly from `app/` and `src/` (tests and `src/i18n` exempt).
70. **German completeness is enforced by the compiler**: `Strings` is the widened shape of the English strings, and `de.ts` plus `de/*.ts` are typed with it, so a missing or extra key fails typecheck. Informal "du"; volleyball terms Zuspieler, Außenangreifer, Mittelblocker, Diagonalangreifer, Libero, Abwehrspezialist.
71. **Language / Sprache** in Settings (English / Deutsch), persisted, kept on "Delete all data"; `<html lang>` follows it on web; the printed sheet follows it too. Position badges keep the international codes (S, OH, MB, OPP, L, DS) in both languages.
72. **Version 2.0.0**: `version` in `app.json` / `package.json` bumped (Android `versionCode` 20000, so it installs as an update over 1.0.0).
73. **Deleting a player** clears every reference to them (court, libero, "libero replaces", substitution events) via `removePlayerEverywhere`, so exports stay importable. Deleting a player who is part of a **played** set is blocked with an explanation (mark them injured, or reset that set's live data) — removing them would rewrite the set's score history.
74. **Locked lineup controls** (court slots, libero slot, bench target, chips, serve toggle) report `disabled` to assistive tech while a set has live data. List-row actions wrap below the name on narrow screens instead of truncating it.

## v2.2 — Team nav bar, presets and starters (PR #21)

80. **Team nav bar** (Roster · Matches · Presets · Starters) is a component inside the team screen, not a nested navigator; the tab is kept in `?tab=` (unknown → roster). It replaces the old Roster | Matches switch.
81. **Data model v3**: `LineupPreset { id, teamId, name, kind: 'starters' | 'preset', slots, liberoId, liberoReplaces, createdAt }` in a `presets` collection; at most one `starters` preset per team. Store version 3 (v2→v3 migration adds `presets: []`), export `schemaVersion` 3; v1 and v2 files are upgraded on import.
82. **Team starters** have their own editor route (`/team/[teamId]/starters`), an empty name with a fixed label, and are saved on the first edit. Starters with nothing filled count as "no starters". **New matches** pre-fill set 1 from complete starters; injured starters are left out (their spots stay empty), and the Starters tab says how many would be left out.
83. **Presets**: created with a name first (default "Preset n"), edited with the lineup builder (preset mode hides the serve toggle and copy-previous), auto-saved; copy → "X (copy)". Names are required, ≤ 40 characters and unique per team ignoring case — also checked on import.
84. **Applying** a preset or the starters to a match set copies court, libero and "libero replaces" exactly, keeps the set's serve choice and events, skips inactive or removed players (with a message), never places anyone twice, and is disabled for played sets (#68). Reasons for disabled buttons are given as accessibility hints, not as permanent text.
85. **Merging an import**: a file's team starters replace that team's existing starters (even under a different id); a second preset with an existing name is a `MERGE_CONFLICT` (like jersey numbers). The merge hint says so. Presets never block deleting a player; deleting a player removes them from all presets.
86. The match lineup logic moved from `useLineupEditor` into a generic `useLineupDraft` used by both the match screen and the preset editor (no behaviour change for match sets).
87. **Version 2.2.0** (versionCode 20200).

## v3 — Match day & stats

### Foundation (orchestrator)

88. **Data model v4**: point events gain optional `kind` (`PointKind`), `playerId` and `at` (ISO time the rally was recorded). Store version 4 — the v3 → v4 step changes nothing, old events stay valid as they are; export `schemaVersion` 4 — v1, v2 and v3 files are upgraded on import. `SetEvent` is now `PointEvent | SubEvent` (named interfaces, same shape).
89. **Point tags** (`src/domain/pointTags.ts`): us → kill / ace / block / opponentError; them → ourError / opponentKill / opponentAce. Only kill, ace, block and ourError may name a player; a player without a kind is invalid. Import rejects incoherent tags and tagged players of another team as `INCONSISTENT_REFERENCES`. A player named in a tag of a played set can't be deleted (extends #73); `removePlayerEverywhere` (defensive) keeps the rally and its kind and drops only the player.
90. **Results are derived, never stored** (`src/domain/matchState.ts`): a set is won at 25 (15 in set 5) with a 2-point lead; the match at 3 sets. The current set is the first set (1–5) nobody has won yet, stored or not. Sets stored after the deciding set (only possible in pre-v3 data) are ignored for the result.
91. **Match duration** = first to last timestamped rally of the counted sets. Rallies recorded from v3.0 carry `at`; matches played before have no duration (shown as nothing, not "0 min").
92. **All statistics, including the tag totals, are computed in `src/domain/stats.ts`** (one place, as the plan says); the point-tagging worker builds the tagging UI and uses those totals.
93. **Version 3.0.0** (Android versionCode 30000). Major version because the store and export formats change (older apps can't open v4 data).

### Statistics (PR #26)

94. **Rotation of a rally** = the rotation it was played in, before the side-out it causes. Received = the opponent served; side-out % = received rallies won ÷ received (shown "–" when nothing was received); break point = a rally won on our serve. Computed by `src/domain/stats.ts` from `replaySteps` (an additive export of `liveSet.ts`; `replaySet` unchanged).
95. **What counts**: a set counts once it has a rally, and only sets that count for the result (#90). Subs in a set without rallies count for nobody; in a played set every applied sub counts (skipped `INVALID_SUB` don't; `SUB_LIMIT` / `REENTRY_RULE` ones do).
96. **Started** = in the stored starting six; **played** = among the six for ≥ 1 rally. The **libero** counts as started and played only if their swap applied in at least one rally.
97. **Serve turn** = a run of our serves by the same server (starts at our first serve and after each side-out; substituting the server starts a new turn for the new server; a server swapped out before serving gets none; out and back with the substitute serving in between = two turns). Points on serve = rallies won while that player served. Tag totals count only tags that name a player.
98. **Stats tab** (5th team nav item, `?tab=stats`): season tiles (record W–L, "n in progress" separately, sets and points won : lost; matches without rallies aren't counted), rotation table, player table. **Match stats** `/match/[matchId]/stats` with a local set filter (All / Set N). Header title is fixed ("Match stats"); the opponent is a heading in the content. Tables keep the first column fixed and scroll the number columns sideways; abbreviations are explained in a legend and in each row's screen-reader summary (EN W L SO% BP · St Pl In Out Sv SvP K A B E; DE G V SO% BP · Sta Gsp Ein Aus Auf AuP Ang Ass Blo Feh).

### Polish (PR #25)

99. **Print with results**: only for a played match (`status !== 'notStarted'`), Print first offers _With results_ / _Lineups only_ / _Cancel_ (in-app dialog). The results section (above the sets) shows won / lost / in progress, sets won, every started set's score (open set marked "in progress") and the duration rounded to minutes, hidden under 1 minute. Unplayed matches print exactly as before.
100. **"Delete all data"** text names saved lineups (presets and team starters) — "gespeicherte Aufstellungen (Vorlagen und Startsechs)". `docs/WORKER_BRIEF.md` rewritten for v3.

### Whole-match live mode (PR #27)

101. **Live mode follows the match**: the scoreboard shows "Sets x:y"; a won set replaces the point buttons with "Set won by …" + **Start set N+1** + **Undo last point** — no rallies or substitutions in a won set (court read-only). At 3 sets a **match summary** shows the result, every set's score and the duration (hidden without 2 timestamps or under 1 minute, rounded to minutes). Opening live mode without a valid `?set` (and the match screen's Live button) goes to the current set, or to the summary when the match is over; the set picker still browses earlier sets ("Go to set N").
102. **Next set setup** inside live mode, for the current set when it isn't stored or is incomplete with nothing recorded: Team starters (if complete) / each preset / Copy set N (applied like the builder: injured or removed players left out, nobody twice), a serve choice, Start (enabled at 6/6), Edit lineup (opens the builder; saves the draft only if something was chosen). The setup is a local draft saved on Start.
103. **Serve default for a new set**: whoever received first in the previous set serves first (set 5 too; the toggle covers a coin toss). A stored set without rallies gets this default when reached from the previous set; a choice made in the setup panel wins. A complete set without rallies goes straight to live play with a serve toggle until the first rally (no extra tap for set 1).
104. **Undo across a set end**: from an untouched next set, the setup panel or the summary, Undo removes the last rally of the previous played set and returns to it (re-opening it). In an earlier won set Undo is hidden once a later set has rallies.
105. **Pre-v3 data**: a set stored after the deciding set shows "Played after the match was decided — not counted" and no live controls.
106. **Result labels** ("3:1 won", "1:3 lost", "2:1 · in progress", nothing before the first rally) on their own line in the match list (also in the row's screen-reader label) and under the set tabs on the match screen. The match screen's five links are one row on wide screens and 3 + 2 on phones.

### Point tagging (PR #28)

### Foundation (orchestrator)

147. **Data model v7** (app 6.0): profiles and players may have a `photoId`, players a confidential `description` (trimmed, 1–1000 characters), and an "our error" tag an `errorType`. 148. **Photos live outside the main store**: one storage key per photo (`volley-lineup-photo:<id>`, `src/store/photoStore.ts`) holding a data URI (≤ 256 px, JPEG quality 0.7, about 10–30 KB). The main store is written on every rally in live mode, so it stays small, and no single stored value grows with the number of photos (Android AsyncStorage has a per-value limit). Data URIs work the same on web and native, and in export files. Photos nobody refers to are deleted automatically when profiles or players change. So save a photo before pointing a profile or player at it, and keep an unsaved form's picture in local state. Screens show the fallback until photos have loaded; export and import wait for them.
149. **Photos are always exported** (owner's choice). Export a team and the photos of that team's profile and players go with it.
150. **Descriptions are exported only when chosen** (owner's choice): Export offers "Include descriptions" only while descriptions are unlocked, off by default (`buildExport({ includeDescriptions })`). **A merge never deletes a picture or description**: an incoming profile or player without a `photoId` or description keeps the existing one; when the file has one, the file wins. Replace takes the file as it is.
151. **Error types** (owner chose the 7-type list): Serve · Reception · Attack · Block · Set · Net / foul · Other. "Net / foul" covers the referee's faults that aren't a skill error (net touch, centre line, rotational / positional fault, double contact / catch, four hits). No type = "unspecified", shown as such in the stats. Plausibility (rules doc §7): a serve error only on our serve and only by our server; a reception error only when they served; a block error only by a front-row player who isn't the libero; an attack error by anyone on court but the libero. `setLastErrorType` also turns an untagged lost rally into "our error"; re-tagging "our error" (e.g. to pick the player) keeps the type.
152. **Performance numbers** (`src/domain/performance.ts`, on top of `stats.ts`, same counted sets and #94–97 rules): _rallies on court_ = rallies the player stood on court for, with that moment's libero swap applied. So the libero counts the rallies they played, and a middle replaced in the back row doesn't count those. _Plus/minus_ = rallies won − lost while on court. _Net points_ = kills + aces + blocks − errors. _Rating_ = the sign of net points when the player has any tagged action, otherwise the sign of plus/minus (positive / even / negative; none without rallies). _Error rate_ = errors ÷ rallies on court; _errors per action_ = errors ÷ (K + A + B + E); _serve error rate_ = serve errors ÷ serves; _attack error rate_ = attack errors ÷ (kills + attack errors); each "–" when its divisor is 0. Performance rows sort by most rallies on court first, then by jersey number.
153. **Routes**: player detail `/team/[teamId]/players/[playerId]` (back → roster); performance `/match/[matchId]/performance?set=N|all&player=ID` (back → match). A match in the player detail's list opens that match's performance view for the player (All sets).

## v8.1.1 — Swipe without flicker (PR #67)

## v10 — Accounts and cloud sync (Supabase)

253. **Owner's choices** (asked once at the start of v10): sign in with a **6-digit code sent by email** (magic links are awkward in Expo Go and the APK); roles **manager** (edits everything) and **player** (views only), no scorer / assistant role; confidential player descriptions **never leave the device**; team and player photos sync to a **private Supabase Storage bucket** readable only by the team's members (256 px as before); profile photos stay local. Amends #55 (cloud sync was out of scope until now).
254. **Backend = the existing hosted Supabase project** "Volleylineup manager" (`qzeergfqfwovcvdarwua`, eu-central-2 Zurich, Postgres 17, free tier). The schema lives as SQL migrations in `supabase/migrations/` (recreatable, self-hostable); every live change goes through a migration file in a PR. The project doesn't grant API access to new tables automatically, so every migration grants explicitly (`authenticated` only; `anon` only on `keepalive`).
255. **Full design in `docs/V10_SYNC_DESIGN.md`** (plan agent, checked and amended by the orchestrator). One release 10.0 (not 10.0 + 10.1): sync without roles is unsafe, roles without view-only are broken, and splitting would ship the v13 shape twice.
256. **Offline-first, record-level sync.** The local store stays the only thing the UI reads. Each team is split into records — `team`, `player`, `season`, `opponent`, `match` (without its sets), `set` (`<matchId>/<n>`), `preset`, `starters` (one per team, keyed by the team id because every device creates its own starters id) — and the most recent save wins per record. Deletions are tombstones on the server (`deleted`, payload null).
257. **Change detection by payload hash, not by stamping actions.** A record is dirty when the hash of its sync payload differs from what the server last had (`base`); the save time is noted when the change is first seen. No store action changes, so every existing test and the export golden stay as they were. Records and their bookkeeping are written in one store update (`syncTransaction`), so a crash can't leave "have server version N" next to older records.
258. **Store v13**: `sync: { deviceId, account, teams }` — device-only, persisted with the data in the same blob, never exported. Export `schemaVersion` stays **10** (the file doesn't change; golden byte-identical). Delete all data also forgets the account and shared teams (the cloud is untouched); deleting the linked profile unlinks the account; an import keeps the sync state.
259. **A team that disappears locally is unlinked, never deleted on the server.** Only an explicit "Delete for everyone" (managers) deletes a cloud team. So "Delete all data", deleting a profile, an import Replace or removing a team from one device can never wipe a shared team for everyone.
260. **Server decides last-write-wins**: `push_records` keeps the row with the later (clamped) client save time, tie-break by device id; client times more than a minute in the future are clamped. Pulls use a server sequence (`version`) with a 10 s overlap, so a slow commit is never skipped.
261. **All backend code in `src/lib/sync/`** behind a small barrel (`startSync`, `syncNow`, `requestCode`, `verifyCode`, `uploadTeams`, `listMembers`, `createInvite`, `joinTeam`, `holdMatch`, …); every command resolves `{ ok, value | error }` and never throws. ESLint forbids `@supabase/*` and `@/lib/sync/*` internals everywhere else. Screens read status and access through hooks in `@/store` (`useSyncStatus`, `useTeamAccess`, `useCanEdit`, `useMatchAccess`). Jest mocks `@/lib/sync` for every test (`src/lib/sync/__mocks__`).
262. **Who may edit** (`src/domain/syncAccess.ts`): local teams always; shared teams only with the manager role (cached on the device, so view-only also works offline and signed out); a shared match held by another device is read-only for everyone else until the hold expires or a manager takes over.
263. **Dependencies**: `@supabase/supabase-js` (the backend client) and `react-native-url-polyfill` (React Native's `URL` is incomplete; imported on native only), both with `EXPO_OFFLINE=1 npx expo install`. supabase-js keeps the session in AsyncStorage (already installed); sign-out is always `scope: 'local'` (the default would sign out every device).
264. **Public config**: the project URL and the **publishable** key (public by design, protected by RLS) live in `supabase/public-config.json`, read by `app.config.js` (`extra.supabase`, overridable with `EXPO_PUBLIC_SUPABASE_URL` / `EXPO_PUBLIC_SUPABASE_KEY` for a self-hosted server) and by the keepalive workflow. The service-role / secret key is never in the repo, the app or a function.
265. **Delete account without an Edge Function**: a `delete_my_account()` SQL function (SECURITY DEFINER, `authenticated` only) deletes the caller's sole-member teams and their auth user; it refuses while the user is the last manager of a team with other members. The app first removes those teams' photos through the Storage API. Simpler than an Edge Function and needs no service-role key (`postgres` may delete from `auth.users` on this project — checked).
266. **New screens and tour pages**: `/account`, `/account/sign-in` (modal), `/account/teams` (upload / download), `/team/[teamId]/members`, `/join?code=`; tour pages `account`, `signIn`, `cloudTeams`, `members`, `join` (not in the quick tour).
267. **Test accounts**: the live-check script and web QA use test users created by SQL (`*@example.test`, password) and deleted afterwards, because the agents can't read the emailed codes. The app itself only offers the email code.
268. **Backend shape** (PR #86): tables are SELECT-only for `authenticated` under RLS; every write goes through SECURITY DEFINER RPCs that check `auth.uid()` and the role on the same team id they write (`create_team`, `push_records`, `create_invite`, `join_team`, `set_member_role`, `remove_member`, `leave_team`, `delete_team`, `hold_match`, `release_match`, `delete_my_account`); EXECUTE is revoked from `public` / `anon`. Policies use set-returning helpers in a non-exposed `private` schema (`team_id in (select private.my_team_ids())`, once per query). Error codes: 42501 forbidden, VL001 last manager, VL002 invite invalid, VL004 last member, VL006 too many teams, VL007 team full, VL008 photos remain, 22023 bad input. The Supabase advisor's "SECURITY DEFINER function executable by authenticated" warnings for these RPCs are intended (listed in `docs/SUPABASE.md`).
269. **Server-side last-write-wins**: `push_records` stores a record only when its (client save time, device id) is newer; the client time is truncated to milliseconds and clamped to at most one minute ahead of the server. Pulls page by a server sequence (`version`); `updated_at` is the clock time right after the version, so with the `authenticated` role's 8 s statement timeout a 10 s overlap never skips an uncommitted write (self-hosted servers must keep that timeout).
270. **Abuse limits on the free tier** (security review): 64 KB per record, 20 MB per team (payload + 512 bytes per record), 20 000 records per team, 10 teams created per account, 150 photos per team (256 KB each, JPEG / PNG / WebP), 20 usable invites and 50 active holds per team, 200 records / 1 MB per push. One account can store at most about 375 MB of photos. Several accounts can still fill the project — the owner keeps the auth rate limits and sets a usage alert.
271. **Invites** (security review): codes are 10 characters (50 bits, no I / O / 0 / 1). Player codes: many uses, up to 30 days. Manager codes: **one use, up to 7 days**. A removed member can't rejoin with a code created before the removal (a new code re-invites them). A code never downgrades a role.
272. **Photos can't outlive their team**: `delete_team` / `delete_my_account` refuse (VL008) while a team still has photos, and `create_team` treats an id with leftover photos as taken — so a re-created team id can never see an earlier team's (minors') photos. The app deletes the photos through the Storage API first.
273. **Member changes are serialized per team** (team row `FOR UPDATE` in the last-manager guard and the member RPCs), so two managers leaving / demoting at once can't leave a team without a manager. Deleting a user in the dashboard is blocked while they are the last manager of a team with other members (make someone else manager or delete the team first).
274. **Migrations on the hosted project** are applied with the Supabase MCP tool and their recorded versions are then set to the file versions (`20261125090000…090600`), so `supabase db push` / migration history stays in step with the files. Other projects: `supabase db push` or psql in file order.
275. **Sync records and repair** (PR #90): starters take the cloud's preset id (no ping-pong between devices); a parent's tombstone is undone when anything below it was saved later (pending edit or a later server save) or, for players, when a played set uses them; set tombstones only apply with their match; a match and its sets are pushed in one batch; orphans are reverted; repair never changes a **played** set for a missing player (reported as `missingPlayer`; the device that still has the player brings it back) and keeps references to players the server may still have; duplicate jersey numbers are reported, not renumbered; duplicate season / opponent names merge into the oldest; duplicate preset names get " (2)". Synced text fields are limited (names 200, other text 1000 characters). Known limit: fields added by a later app version are dropped when an older app edits that record (zod strips unknown fields) — a future schema change must keep that in mind.
276. **Viewer UI** (PRs #87, #89): edit controls are hidden, not disabled (exceptions: the serve toggle stays visible but disabled, the roster's active switch becomes plain text); one `ReadOnlyNote` explains why ("View only: only managers can change this team." / "Being scored live on Anna's device." + Take over for managers). Editor routes (player form, new season, new match) show a view-only screen instead of the form. Viewers watch live mode read-only (score, court; no setup of the next set) and the app polls every 15 s while they watch.
277. **Live hold** (PR #87): every manager device of a shared team that opens live asks for the hold (claim on mount, refresh every 5 min, release when the last live screen of that match closes — stacked screens share one hold). Take over from the match screen opens live. A held match is read-only on the builder too.
278. **Deleting a shared team** (PR #89): managers choose "Remove from this device" (the team stays in the cloud and can be downloaded again) or "Delete for everyone"; players "Remove from this device" or "Leave team". The team is unlinked before the local copy is deleted, so the sync never reads an empty linked team. **Import**: shared teams are never removed or replaced by an import; a manager's copy in the file is merged (file wins per id), a viewer's copy is skipped; when a Replace clashes with a shared team (e.g. a reused jersey number) nothing changes and a specific message says why.
279. **Members and invites UI** (PR #88): the team header shows "Members" (shared) or "Share" (local team); only active invites are listed, soonest expiry first; role / remove controls only on other members' rows (you leave with Leave team); "Share" uses the phone's share sheet (web: `navigator.share`, else the clipboard copy) with the code and a join link (`volleylineup://join?code=…` on phones, the web `/join?code=…` on the web); the code is checked on the device before joining; members without a name sort last within their role. Members see display names (the profile name), never emails.
280. **Accounts UI** (PR #91): the Profile tab's "Cloud sync" card offers Sign in, or shows the email, status and Account; an account linked to another profile is named and can't be signed in from here. Sign out / Log out ask first only when changes are still waiting. Delete account checks first: blocked teams are listed with a link to Members; otherwise the confirm names the teams that will be deleted for good. On first sign-in a local team that is also in the cloud appears under Download only (the cloud copy wins). The German UI says "Trainer" for manager and "Vom Konto abmelden" for signing out of the account (Profile → "Abmelden" leaves the profile).
281. **Sync engine** (PR #92): one cycle under a mutex (memberships → per team: pull every page → download referenced photos → merge in one store update → push; then holds). Triggers: app start (after the screen is idle + 1.5 s, because the first change detection hashes every record), app to foreground, 3 s after a change, every 60 s in the foreground (15 s while watching a shared match live), Sync now; nothing in the background except one last push. **No network call and no store subscription** for users without an account and without shared teams. Offline: exponential back-off (10 s → 30 s → 2 min → 5 min); the status says Offline with the number of waiting changes; nothing is thrown to a screen.
282. **Edits are stamped when made, also offline** (review blocker): the save time of every local change is recorded right after the change (and before every cycle), online or not — otherwise an older offline edit would beat a newer one made elsewhere.
283. **A refused push of this device's own earlier save** (clock moved back, two saves in one millisecond) is re-stamped to just after the server's time and pushed again, so the user's change is kept and nothing is re-sent forever. ## v10 audit (after 10.0.0)

Findings, evidence and what was left: `docs/AUDIT_V10.md`.

292. **Invite codes end with the access of the people who know them** (audit H1). A code works for any account that knows it, so: when someone stops being a manager of a team (made a player, removed, left, account deleted) the team's open **manager** codes are revoked (a trigger on `team_members`); **removing a member revokes every open code** of the team — the managers create new ones for people who haven't joined yet (the Remove question says so). Chosen over "revoke only what the removed member could know": invites aren't tracked per person, and a removed manager has seen all of them. `create_invite`, `set_member_role` and `remove_member` check the caller's role again once they hold the team's row lock. Migration `20261126120000_v10_audit_invite_revocation.sql`; rls.sql T31–T33.
293. **The app reads `max_uses`** (audit H2, H5): a used-up manager code is no longer listed as an active invite, and "New invite" offers manager codes for 1 or 7 days only (the server refuses longer ones).
294. **A shared team's cloud photo keeps its `photoId` although the picture isn't on the device** (audit H3). Whether a photo id is a cloud photo is read from the stored sync state (`sync.teams[id].photos`), not from an in-memory list: the photo prune leaves such ids alone after a restart, every pull fetches the ones the device lacks, and photos that arrive with a refused push's newer row are listed at once. A `photoId` the cloud never had (a local save that failed) is still cleared. Not changed: a photo the cloud answers "not found" for (AUDIT_V10 M18).
295. **The pull cursor's 10 s overlap counts from the first page's server time** (audit H4), so a pull of several pages never passes a row that was younger than 10 s when it was read.
296. **A shared team that leaves the device is unlinked in the same store write** (audit C1; amends #259 and design §3.10, which left it to the next pull — but signed out no pull runs). `deleteProfile`, `deleteTeam` and `replaceAll` drop the links of the teams they remove; the engine drops links 10.0.0 left behind at start and whenever it notes changes, without a session; the import treats a linked team as shared only when it is on the device. A backup restored after "delete profile" is an ordinary local team; downloading the cloud team again links it with "the cloud wins".
297. **Import: read and write in one step** (audit H10). The file's photos are added first; then the current data is read, merged and written without waiting in between, so a sync cycle can't slip in and be undone. Photos nobody refers to afterwards are removed by the existing prune (`replacePhotos` is no longer used by the app).
298. **Merge refuses a file that holds a shared team's records under another team** (audit H9): same record ids, other team id — a backup from before the team got a new id on upload, or a co-coach's export. The message is the existing "clashes with a team shared on this device". Replace is unchanged (it keeps the shared team's records).
299. **A promotion resets the local copy first** (audit H8), exactly like a demotion: the stored role stays `player` until the reset pull has worked. The role of an already linked team is only changed by the cycle's membership check (not by Join / Download directly).
300. **Outages don't sign the device out** (audit H7): for the auth API, an HTTP status ≥ 500, and a 429 on a token refresh, are passed to supabase-js as a network error (`src/lib/sync/authFetch.ts`), because auth-js deletes the session on any refresh error outside its own list (500–504, 520–530) and a paused project answers 540.
301. **Duplicate jersey numbers are shown** (audit H6): two devices can each add a player with the same number before syncing; both stay (as designed, #275), but the backup file is refused on import until one is renumbered. The Roster tab and Settings → Export now say so, derived from the stored players (so it also shows after a restart).
302. **No new app version by the audit**: the fixes are on `main`; releasing 10.0.1 is the owner's decision (recommended, see AUDIT_V10). The store version stays 13 and the export schema 10 — no stored shape changed.
303. **After the independent review of the audit fixes**: (a) a reset pull (demotion, promotion, a viewer adopting an old copy) leaves the sync bookkeeping **exactly matching the device** — entries the cloud never had are dropped; rows the device can't apply (invalid here, an id of another local team), orphans and players it can't read are left as the device has them — so a device that becomes a manager pushes nothing it shouldn't; a promotion is armed once per app run. (b) A link without a team on the device never adopts a team an import brings under its id (also a download that hasn't pulled yet); the team is then local and "Download" links it with "the cloud wins". (c) The import computes first, puts the result's photos in memory and replaces the store in the same step. (d) The AFTER triggers on `team_members` are `security definer` (migration `20261126130000`): a user deleted in the dashboard is deleted as `supabase_auth_admin`, which has no rights on the app's tables — on 10.0.0 that deletion failed for every team member. The same migration revokes, once, every open manager code and every open code of a team with a later removal (codes from before `20261126120000` that could have outlived a demotion or removal; none existed on the hosted project). Accepted as they are (AUDIT_V10 "After the fixes"): the revoking statements skip codes that expire in the same instant, `join_team` briefly locks the team row for a revoked code too, and the duplicate-number text says "two players" for three.
304. **Owner's answers to the audit's open questions** (2026-11-26): (1) removing a member keeps revoking **every** open invite code of the team (#292 confirmed); (2) **no CAPTCHA** on sign-in — the auth rate limit ("emails per hour" at 20 or less) is the brake (AUDIT_V10 M8 accepted); (3) the email code stays **6 digits** (L14 accepted); (4) and (5) are built: #305, #306.
305. **"I already have a code"** on the sign-in screen (audit M13): opens the code step for the typed email without sending an email, so a user who closed the screen (or the app) while looking for the code doesn't request another one. The code step then says "Enter the newest code we emailed to …; a code works for 10 minutes" (the project's `otp_expiry`, `supabase/config.toml`) instead of "We sent a code", and "Send a new code" has no wait (nothing was sent). Not done: remembering `{email, sentAt}` across an app restart, and own texts for a failed send by the mail server.
306. **A taken-over match is no longer saved from the previous scorer's device** (audit M1; amends #277, #281, #288). A sync cycle reads the live holds **before** it pulls and pushes (it was last). A match this device was scoring — its own hold was the last one it knew **and hadn't run out** — that another device holds now is **yielded** while that hold lasts (`yieldedMatches` in `src/domain/syncAccess.ts`, kept by the engine in `src/lib/sync/holdState.ts`; a refused 5-minute hold refresh yields at once): its `match` and `set` records aren't pushed from here, and a row another device saves for them replaces this device's unsynced change **whatever the save times say**, with a notice ("Anna took over scoring a match of …; 1 change made here that hadn't synced yet was undone"). **Held back, not thrown away**: a change the scorer never saved over stays on the device and is synced when the hold ends (released, run out, or taken back here — taking back pulls while still yielded, so it starts from what the other scorer saved). Chosen over discarding at once: a take-over by someone who then scores nothing must not cost the rallies scored here. **Only a running hold can be taken over**: a device whose own hold had run out (the scorer in a hall without a connection for more than 15 minutes) doesn't yield to a device that merely claimed the free match — e.g. the previous scorer's still-open live screen, which re-claims every 5 minutes — and "the latest save wins" as before; found by the independent review, where the first version let such a re-claim wipe the real scorer's offline rallies. This device's own earlier save coming back (a push whose answer was lost) never counts as the scorer's. A device that **never held** the match is not affected ("the latest save wins", as before): holding back there would strand a whole offline-scored match behind someone who merely has the live screen open.
307. **The take-over block lives in the app; the server's hold stays advisory** (no database change; #277 stands). Known limits (in all of them "the latest save wins", as on 10.0.0): the new scorer's hold has already ended (it left live) before the old device syncs again; the old device's own hold had run out before it learned of the take-over (offline for more than 10–15 minutes); a device clock that is minutes off (expiry is judged by the device's clock); the yield is remembered for the app run only (after a restart the device follows "the latest save wins" again — it isn't scoring then); a push already under way when the take-over happens can still land; a 10.0.0 app doesn't yield; if the hold list can't be read (a server error) the teams still sync with the holds known so far and the status shows the error; deleting a held match is still not blocked (AUDIT_V10 M15). `SyncNotice` gets the kind `takenOver` — notices are runtime-only, so the stored shape is unchanged (store 13, export 10).
308. **Still no new app version**: the two follow-ups are on `main` with the audit fixes; the owner decides about the release (#302).

## v10 audit: the engine findings (second chat, after 10.0.0)

317. **An idle sync cycle writes nothing** (audit M19). The engine's store transaction doesn't call the store when its callback returns the same state: zustand's persist rewrote the whole stored data after every `set`, also for "no change" (1 + 2 × shared teams full writes per cycle). One thing the redundant writes did by accident is kept on purpose: a write of the data that **failed** (storage full or briefly unavailable) is repeated by the next cycle. `lastStoreWriteFailed()` (`src/store/appStore.ts`, a wrapper around AsyncStorage) says whether the newest write worked — the newest by start, because writes finish in the background and not always in order — and while it didn't, a "no change" transaction still goes through the store.
318. **A linked team that can't be shown yet is not downloaded again and again** (audit M6). A team that isn't on the device because its own `team` record is missing in the cloud (the creator's first save hasn't arrived, or was refused) or can't be read by this app version used to be pulled from version 0, with its photos, every cycle. Now, for such a team: nothing is merged, written or downloaded; the engine remembers **for the app run** where the last complete pull got to (`EngineCore.awaited`: an in-memory cursor that follows the stored cursor's 10 s rule, and the version of the `team` row it saw) and only asks for what is new; only a newer `team` row causes one more complete pull. Chosen over a timed back-off ("once per app start", the audit's suggestion): the team appears as soon as its record is saved, and waiting costs one small request per cycle. The stored cursor stays 0 and nothing new is stored, so the first cycle after a restart pulls completely once. The user gets a notice (kind `waiting`, runtime only: "One of your shared teams can't be shown yet…"), taken back when the team arrives. Also on purpose: such a team **stays linked** when the cloud team holds deleted records — before, the merge stored their bookkeeping and the link was then dropped without a word as "deleted here" after one cycle.
319. **A new store version pulls every shared team once more from the start** (audit L6). Rows this app version refuses are skipped, and once the pull cursor has passed them they never come again, also not after an update that could read them. Every store migration step from v13 on now sends the pull cursor of every team that has pulled before back to the start (`withPullCursorsReset`): to **-1 (`REPULL_CURSOR`), "pull everything again and merge it the normal way"** — records the device has are skipped by their version, the rest is merged as on any pull. Not to 0: a view-only team with cursor 0 and bookkeeping gets the "replace by the cloud's copy" pull (#284, #299), and the independent review showed that pull losing data on view-only devices in three ways (it deletes the device's copy of a record whose newest row it still can't read, with everything below it; it skips what changed meanwhile when the team's own row is such a row; it never brings a deleted player back into a lineup). -1 is a value of the existing number field, read the same way by every released version (a pull from below every version), so the stored shape is unchanged; a cursor at 0 stays 0. The store version stays **13**, so nothing runs today. **Rule for later versions: an app version that accepts more synced data than the one before (a new field or kind, a longer text) must bump `STORE_VERSION`**, also when the stored shape itself doesn't change. Chosen over a separate "sync schema version" key in storage and a marker field on the team's sync state (both new stored state), and over keeping the cursor below skipped rows (they would be downloaded again every cycle). Not covered: rows skipped because their id belongs to another team on the device, or whose parent wasn't there, are still not pulled again when that cause goes away (the next store version heals them too).
320. **From the independent review of #317–#319** (PR #105): (a) the stored data also counts as "not the newest" when two writes both worked but the older one landed last (`lastStoreWriteFailed`); (b) a team is only waited for, and only gets its notice, while it is still linked after the request that looked for it (an import or "Delete all data" during the pull left the notice behind for good); (c) the "replace by the cloud's copy" pull itself keeps its three weaknesses where it still runs — after a demotion or promotion and when a viewer joins over an old local copy: there the device's own copy can lose records as described in #319 (the cloud and other devices are not affected; nothing is pushed). Hardening that pull is left as a follow-up (AUDIT_V10 "Engine fix log").
321. **A record this app couldn't read back itself isn't pushed** (audit M3). Before a push every change goes through the validation that pulled records must pass (`parsePayload`; `sendableChanges` in `src/domain/syncChanges.ts`). A record that fails — a name over 200 characters, another text over 1000, or data that isn't as expected — stays on the device, counts as waiting, and a notice names it (kind `unsent`, runtime only; "… can't be synced: a name is longer than 200 characters …", taken back when nothing waits any more). Pushed, it synced to nobody, and as a team's own record it kept the team from being downloaded. **New records below a waiting new record wait with it** (the opponents, matches and sets of a new season; everything of a new team whose own record waits; a new match with all its sets when one of them waits): pushed without their parent, the other devices skip them as orphans and never pull them again when the parent finally arrives. A record the server already has doesn't hold what is below it, so a match record that waits never stops its sets — live scoring — from syncing. Photo clean-up is skipped in a push that holds a team or player record back (the cloud's row may still show the old picture) — but not when a record only waits because its new picture couldn't be uploaded: the clean-up is what makes room in a full folder (150 photos), as before. The name fields also take no more than 200 characters now (`maxLength`; the forms' own tighter checks are unchanged). Trade-off accepted: such a record is no longer in the cloud at all (before, it was there but unreadable for every device of the same version). **Added after the independent review:** (a) **the deletion of an opponent waits while the change of a match the server has is held back, and the deletion of a season while that of such a match or opponent is** — the server's copy may still be below it, and every other device deletes what is below a deleted season or opponent (a match moved to an opponent that can't be pushed, its old opponent deleted: the other devices lost the played match). Which season or opponent the server's copy is under isn't known on the device, so all of them wait; they go by themselves once the held record goes. (b) The notice follows what waits: it is replaced when the number of records, the first record or the reason changes, stays away after a dismiss while nothing changes, and goes when the team is unlinked, left, removed from the device, or the account is demoted or removed (`forgetHeld`, `EngineCore.unsent`).
322. **A push the server refuses for its content is taken apart** (audit M4). `push_records` refuses the whole batch for one bad record (SQLSTATE 23514: an id over 200 characters or a payload over 64 kB; 22023: a malformed batch; 22P05: a character the database can't store), and the engine tried the same batch again every cycle: nothing of the team was saved any more. Now the batch is pushed again in halves until the refused group is found (a match travels with its sets; when the server already has the match, each record alone). That group is remembered for the app run by its content (`EngineCore.refused`), waits with whatever new belongs below it (#321), and is only sent again once it has changed or the app restarted; the rest is pushed. The same `unsent` notice says "the cloud refused it". Other refusals (no rights, the team's storage limit VL007) end the push as before. Known limit: an opponent whose id is over 200 characters — data upgraded from before seasons with a long non-Latin name — and its matches stay on this device only; the user can't change an id (see AUDIT_V10 "Open questions" 9). **Added after the independent review:** (a) **the deletion of a season or an opponent travels in one request with every change of seasons and opponents and of matches the server has** (`sendableChanges` returns them as `together`, `pushGroups` keeps them in one group, the deletions last; a changed set of such a match still travels on its own). A push taken apart like this, or split into small batches after a timeout (#323), takes several requests, and another device can pull between any two of them: one that saw "opponent deleted" before "match moved to another opponent" deleted the match with the opponent and never got it back; one that saw a new opponent before the deletion of the old one of the same name took the two for doubles, merged them and deleted the new one for everybody. In one request the server stores all of it or nothing. A first version that only sent such deletions last fixed the first case and opened the second (found by the second review round). When the server refuses that group, its records are sent one by one to find the refused one, and the rest travels together again; a group that times out is tried whole once more and, on a connection that has timed out before in the app run, goes in parts (deletions last) rather than not at all. In those pushes the second case can still happen. A push ends with its error after `8 × changes + 16` refusals — it can't be reached as far as known, and keeps a mistake in this loop from spinning for ever. (b) **A text with half of a character pair** (a lone surrogate: what is left of an emoji cut in the middle, as the 60-character cut of old opponent names can leave it) is refused by the database for the whole request with SQLSTATE 22P02 (checked on PostgreSQL 16; the API layer in front of it may answer differently). Such a record is held back on the device before the push (`textIsWhole`, reason "the cloud refused it"), and 22P02 counts as refused content like the other three.
323. **A push that times out is tried again in smaller parts, and a request that sends a lot gets more time** (audit M5). A request's time until its answer starts grows with what it sends (`requestTimeoutMs`: an uplink of 4 kB/s still gets it through, at most 60 s; 15 s as before for small requests) — a 256 kB photo no longer needs 17 kB/s. A push batch that still gets no answer is pushed again in parts of at most half its size, and later batches stay that small for the app run (`EngineCore.pushLimit`, never below 16 kB: when that little gets no answer the connection is gone, not slow). After two timeouts in one push the cycle ends as offline and the next one continues with the smaller batches. "No connection at all" is not taken for a slow one: only a request that timed out counts (`isTimeout`), and a batch of one group or under 16 kB is never split.
324. **A request also ends when its answer stalls** (audit M12). The timer used to stop when the answer's headers arrived; a body that stalled after them was waited for without end and blocked the sync queue (on the web; React Native's `fetch` only answers once the whole body is there). `fetchWithTimeout` now reads the body itself and gives up when nothing has arrived for 15 s — a pause limit, not a limit for the whole body, so a large download on a slow connection still finishes — and hands on the same answer with the body already there. A stalled answer is a `TypeError` with fetch's own "Network request failed" message, so every layer treats it as offline.
325. **Nothing a live match needs is deleted while another device scores it** (audit M15; extends #262, #277). A match that another device holds (an unexpired hold of another device) has no Delete in its season's list; its season can't be deleted (the form says why); a player who stands in one of its lineups can't be deleted; and its team can't be deleted "for everyone" ("Remove from this device" still works). Each of these actions also asks again at the moment the question is answered, with the matches and lineups of that moment (a match that arrived, or a player the scorer put into the lineup, while the question was open). `heldMatchIds` in `src/domain/syncAccess.ts`, `useHeldMatches` / `canEditMatchNow` in `src/store/syncHooks.ts`. **An import is refused while another device holds a match the file would change** (found by the review; `importChangesMatches` in `src/domain/syncImport.ts`, the import's error `LIVE_MATCH`, a text in English and German): the file's older copy of the match replaced the scorer's rallies here, was pushed as this device's newer save and took them from every device, with Merge and Replace alike. A file that leaves that match as it is can still be imported; a file that brings a scored match the device hasn't pulled yet is refused too. All of this reads the same hold status as the take-over rule and changes nothing in it (`yieldedMatches`, #306–#307). Known limits: the holds are only known from the first sync cycle of an app run on (and not at all offline), so a delete or an import before that still goes through; the gate is in the app, the server would accept the deletion.
326. **A dialog acts on the rights of the moment it acts** (audit L18). The delete confirms of matches, opponents, presets, seasons and players read the role again when the question is answered (`canEditTeamNow`), and the preset name dialogs are closed when the device becomes view-only (closed, not hidden: they don't come back by themselves after a later promotion). The editor screens already switch to the view-only screen on a demotion.
327. **A refused hold without an end gets the server's 15 minutes** (audit L17). When the server refuses a claim without a readable end time, the hold this device notes for the other device ends 15 minutes later (the server's lifetime of a hold that isn't refreshed) instead of never: an unreadable time counts as "still running" (`holdStatus`, unchanged — the take-over rule relies on a refused refresh yielding at once), and offline no sync would replace it. The next sync knows better.
328. **A photo the cloud answers "not found" for keeps its place** (audit M18; amends #285, #294). Its id stays in the team's cloud photo list (it was taken off, so after the next restart the prune cleared the `photoId` and a manager device pushed "no photo" to everyone), and the prune never clears the `photoId` of a record that is exactly what the server last had (`isUnchangedRecord`). **Such an id goes back on the list when the list doesn't name it** (`withCloudPhotos`; a list app version 10.0.0 already shortened) — otherwise the record's next change would clear the `photoId` after all, and the picture would never be asked for again. A `photoId` this device set itself whose picture was never saved is still cleared. The download is tried again every cycle, as before. **Before a team or player record with a picture is pushed, the device asks once per app run and team what the cloud folder really holds** (`checkFolder`, one small request): a listed photo that isn't there is uploaded again with the record by a device that has it — also after a restart, and from a device that always had the picture and so never asked for it. Both added after the independent review: the first version protected a shortened list only until the record was edited, and uploaded a lost picture again only within the app run that had learned of the loss (`main` did so after a restart too).
329. **An import doesn't fail because a shared team's picture is still to be downloaded** (audit L31). `importWithSharedTeams` lets such a picture stand in as an empty photo while the result is checked and takes it out again. No stand-in is made for a photo the file brings: the real one must win, so a backup can also bring the picture back — on a view-only device too, where the first version let the stand-in push it out (found by the review). A missing picture of a team that isn't shared is refused as before.
330. **M7 is not built; the choice is the owner's** (AUDIT_V10 "Open questions" 10). Keeping an old local copy when the same team is joined again as a player needs new ids for every record of the copy (the cloud's records have the same ids, and a pulled record whose id another local team uses is skipped), and leaves two teams with the same name on the device. Nothing was changed: joining still replaces the old copy with the cloud's, as on 10.0.0.
331. **How long the previous scorer's device gives way is not changed** (AUDIT_V10 "Open questions" 11; #306–#307 stand). The review of #325–#329 found that a device which gave way to a new scorer keeps giving way after that hold has run out without its knowing (it was offline): a later ordinary claim of the free match makes it discard its own rallies again. The one-line change that would make this case "the latest save wins" loses data in the opposite case, which works today — the new scorer kept scoring the whole time, and the old device's stale copy of the set would replace everything entered since (checked with a probe: three rallies lost everywhere). The device can't tell the two cases apart; the server could, if it said when a hold began (a database change). Left to the owner.
332. **M2 (clock skew) is not merged** (AUDIT_V10 "Open questions" 12 and "Engine fix log", PR 4). Noting changes in the server's time was built (an offset measured at every pull, kept in memory, dropped when the device's clock and `performance.now()` move apart; the device's clock whenever the server's time isn't known) and got the two-device cases right. The independent review showed that one device then notes times with two clocks, so that its own earlier save can beat its own later change after a lost answer, a restart, the phone sleeping or a slow first pull — seven sequences that keep the later change today. The reviewer's fix narrows this but leaves two windows, and a slow pull makes a right clock up to ±5 s wrong. The owner's condition (safe for devices that are offline, have never pulled, or restart between edits) isn't met, so conflicts are still decided by the devices' own clocks (a fast one wins for at most a minute, #281). The code is parked in a draft pull request. Ways forward: versions decided on the server (a database change), the app-side design with one more merge rule and review, or leaving it and asking for automatic time.

(9) Opponents whose id the server can't store are **not** re-keyed: it only affects opponents carried over from before version 7 with very long Cyrillic or Chinese names, and a notice already tells the user; they stay on that device (#322). (10) An old local copy when a team is joined again: **ask first and offer a backup** — small, and no second team with the same name (#334; #330 is superseded). (11) How long the previous scorer's device gives way: **left as it is** — today's choice protects the person who is actually scoring (#331 stands). (12) Clock skew (M2): **left as it is, the draft pull request #109 is closed** — phones keep automatic time, the server already limits a fast clock to one minute (#281), and the proper fix changes how every conflict is decided on the server (#332).
334. **An older copy of a team is only replaced when the user says so** (audit M7; supersedes #330). A team that was unlinked stays on the device as a local team with the same id. No command links the cloud team over such a copy by itself any more (`isUnlinkedCopy` in `src/domain/syncAccess.ts`): `joinTeam` makes the account a member but leaves the copy alone and answers `localCopy: true` (the same code again in the same app run sends no second join — a manager code works once — as long as the server still lists the membership); `uploadTeams` answers the new `inCloud` for a copy of a team the account already belongs to (before: linked, as `linked`) — unless this app run itself asked for the team to be created and got no answer, the cloud team has no records yet and the account manages it: that is this upload, not a copy, and it is linked and pushed as before (an empty cloud team alone doesn't say so: the account's other device may have created it); `downloadTeams(ids, replaceCopies)` links a copy only when its id is in `replaceCopies` and returns the ids it left alone.
